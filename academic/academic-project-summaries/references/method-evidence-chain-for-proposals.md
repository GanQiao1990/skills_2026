# 新方法 / 执行层 proposal 的 evidence chain 写法

适用场景：
- 用户说“新方法需要详细证实”
- 用户说“这一层太虚”“增加具体调控内容”“怎么调节”“什么结果证明成立”
- 需要把平台型方法或执行层模块写得更像高分期刊 / 高水平基金文本

## 一、平台/新方法的硬证据链

默认按以下顺序展开，不要只写“将进行验证”：

1. benchmark
   - 比什么：时间、算力、throughput、候选多样性、阳性命中率、阳性富集倍数、后续部署保留率
   - 目标：证明不是简单增加复杂度或工具拼盘

2. 候选压缩 / 富集
   - 跟踪候选从初始集合到最终入围的淘汰轨迹
   - 目标：证明不是“越筛越少”，而是“越筛越准”

3. ablation
   - 去掉关键步骤分别比较
   - 目标：证明每一步有独立贡献

4. control matrix
   - 阳性、阴性、结构破坏、接口破坏、时序错配、表达量对照
   - 目标：证明效应不是非特异负担或伪阳性

5. function bridge / 终点闭环
   - 设计层信号 → 筛选层富集 → 执行层因果成立 → 生产终点受益
   - 目标：证明方法不是停留在 surrogate readout

## 二、执行层段落的固定写法顺序

当写 4.4 / 4.5 这类执行层时，默认用下面五步，而不是抽象概念说明：

1. 为什么选这个调控轴/节点
   - 必须落到主因果链：是否直接连接状态感知、执行节点、代谢池和产量终点

2. 具体调控什么分子事件
   - 例如：提高 NtrB→NtrC 有效磷酸转移效率
   - 而不是笼统写“增强氮同化”

3. 怎么调控
   - binder 连谁
   - linker / proximity scaffold 怎么用
   - 是否有三类构型并行（低 basal、生产期诱导、条件响应）

4. 调控目的是什么
   - 避免生长前期代谢负担
   - 仅在生产窗口增强状态输出
   - 将状态增强传递到具体执行节点

5. 应得到什么结果才算成立
   - 用“结果模式”写，而不是只列 readout 名称
   - 例如：reporter 定向增强 → Gln/Glu pool / 15N 流增强 → 产量提升，且主要发生于生产窗口

## 三、动态调控模块的默认硬写法

动态调控模块若涉及生长—生产切换，默认写：
- 生长前期低干预
- 达到目标生物量后进入生产窗口
- 此时启动 proximity / binder 模块

必须说明：
- 为什么不在全程高表达
- 为什么生产窗口激活更合理
- 与静态过表达相比希望解决什么问题（背景泄漏、代谢负担、阶段错配）

## 四、酶邻近模块的默认硬写法

必须区分：
- 真实邻近效应
- 简单共表达效应

正文里默认写三类对照：
1. 几何构型对照
2. 表达量对照
3. 功能对照（催化死、接口破坏）

并明确写预期三级结果模式：
- 局部中间体变化
- 关键酶功能 / 局部通量变化
- 终点收益变化

## 五、mimic / 虚拟代谢结果的边界写法

当已有 mimic、virtual metabolism、proxy 数据时：
- 只能写成“模块优先级与实验顺序的前期支持”
- 不能写成方法成立的主证据
- 不能写成“已经证明策略有效”

推荐用途：
- 解释为什么先做 A 模块，再做 B 模块
- 解释为什么某主轴优先于另一个候选主轴
- 解释哪些状态组合值得优先实验

不推荐用途：
- 直接作为 4.4 / 4.5 成立的主证明
- 直接替代实验 readout、时间过程和对照矩阵

## 六、常用高硬度句式

推荐：
- 本项目拟调控……
- 其直接目的是……
- 之所以这样设计，是因为……
- 若该模块成立，预期应首先观察到……其次……最后……
- 只有同时出现上述结果模式，方可说明……

少用：
- 有望
- 可能提供新路径
- 可作为候选方案
- 或许可以实现

当用户明确要求“proposal 更硬”时，应优先把软句改成带判定逻辑的句式。
